# rex: the TUI app (design, no code)

Date: 2026-11-28. Status: **design for review; no code exists yet.** Builds on
`docs/design/2026-11-28-rex-architecture.md` (owner decisions: `rex` = the py_tvision TUI app, `ai-rex` = the engine
command; kiko bundled; one install folder; py_tvision copied in unchanged). Where this document and the architecture
document differ, the architecture document's owner decisions win.

## 0. What rex is, in one paragraph

`rex` is a full-screen terminal application in the Turbo Vision style: a menu bar, a desktop with windows and
dialogs, and a status line. Its main window is a chat with the agent (streaming answer, tool calls as collapsible
entries, diffs in a DiffView, permission questions as dialogs). Around the chat sit panels for every setting,
including the full kiko control that the tray offers today (models with key, ping, enable and roles; Export/Import
wizard; doctor; costs; logs), so the tray becomes optional. The agent runs **in the same process** (the library
`lib_runtime_rex`, its public `Agent`), and so does kiko (`kiko_runtime_lib.Server`), both from the one install
folder. It runs in Windows Terminal, conhost/PowerShell, Linux terminals and the Linux text console, FreeBSD vt and
syscons without X, and IDE terminals (IntelliJ, VS Code). Mouse is optional; every action has a key and a menu item.

What rex is **not**: a new engine (all agent behaviour stays in the library), a replacement for `ai-rex` in pipes or
dumb terminals (`ai-rex` keeps the plain REPL), or a GUI.

### 1.2 Chat while the agent works (streaming)

```
░║ rex                                                                                        ░║░
░║   ▸ bash     python -m pytest -q                                  … running  12 s          ░║░
░║   ▾ edit     tests/conftest.py                                    ? asking                 ░║░
░║   │ @@ -12,6 +12,9 @@                                                                       ░║░
░║   │      import sys                                                                         ░║░
░║   │ +    ROOT = Path(__file__).resolve().parents[1]                                         ░║░
░║                                                                                            ░║░
░║   Three tests fail. The first one is the same root problem; the other two are a            ▒║░
░║   timing issue in the JSONL smoke test. I am looking at the timeout now▌                   ░║░
░╟─ prompt ── Esc stop · type ahead, Enter queues the next message ────────────────────────────╢░
 F1 Help Esc Stop F10 Menu │ ctx 61% │ ● kiko ok │ sonnet │ git-bash │ ab 213/1024 │ ⠹ 14 s  1.2k tok
```

- Tokens appear at the end of the open `rex` entry (`▌` = the stream cursor). The view follows the tail only when
  it was at the bottom; when the user scrolled up, it stays (py_tvision `Terminal` rule) and the frame shows `▼ new`.
- The prompt stays editable while the agent works. Enter while busy **queues** one message (shown greyed in the
  transcript as `you (queued)`); it is sent when the turn ends. A second Enter replaces the queued text.
- Status line shows a spinner, elapsed time and output tokens of this turn instead of `idle`.

### 1.3 Permission dialog (command)

```
              ╔═[■]══════════════ rex asks: run a command ════════════════════╗
              ║                                                               ║
              ║  Tool     bash  (git-bash, C:\Program Files\Git\bin\bash.exe) ║
              ║  Folder   C:\private\rex                                      ║
              ║  Why      rule: ask (commands always ask)                     ║
              ║                                                               ║
              ║ ┌───────────────────────────────────────────────────────────┐ ║
              ║ │ python -m pytest -q tests/test_jsonl_bridge.py           ▲│ ║
              ║ │                                                          ▼│ ║
              ║ └───────────────────────────────────────────────────────────┘ ║
              ║  "Always" remembers: command prefix `python -m pytest`        ║
              ║  for this session only                                        ║
              ║                                                               ║
              ║   [ Allow ~o~nce ]  [ ~A~lways ]  [ Always for ~f~older ]  [ ~D~eny ] ║
              ║                                                               ║
              ╚═══════════════════════════════════════════════════════════════╝
```

- Buttons map 1:1 to the engine's answers: `allow_once`, `allow_always`, `allow_always_folder`, `deny`
  (`core/agent/gate.py`). "Always for folder" is shown only when the request offers a folder
  (`PermissionRequest.remember_folder`); its label names the folder (`Always for src/`).
- The "remembers" line is `PermissionRequest.remember` in plain words, plus where it is stored (allow buffer for
  paths inside the workspace; session only for commands unless a permissions file is set). Nobody has to guess what
  "always" means.
- **No default button.** Enter does nothing until a button has focus; Esc = Deny. The dialog **drops keys for
  400 ms after it opens and discards type-ahead queued before it opened**, so an Enter meant for the prompt can
  never approve a command (section 4.6).
- The detail box is a RichView (scrollable, copyable, never interpreted). Long commands wrap.

- The edit tool already puts a unified diff into `PermissionRequest.detail` (`core/tools/edit.py`, `make_diff`); a
  new file (`fileops write`) is shown as a diff against empty. The dialog uses py_tvision `DiffView` (done:

| Tab | Fields |

| Context | window override, compact at %, warn at %, keep recent messages |
| Kiko | mode embedded / external / off, port, autostart, home folder (read-only, inside the install folder), Claude CLI gateway on/off, monthly cap (read from kiko costs) |

Rule (decided here, plain words): **rex has one source of truth, its settings file in the install folder.**
Inherited `AI_REX_*` variables do not change rex's own agent; the Paths tab and the doctor list them so nothing is
silent. When rex starts an `ai-rex` child process, it builds the child's environment from these settings (inherited
`AI_REX_*` removed first), exactly as the architecture decision says ("rex passes its settings to the `ai-rex`
processes it starts as environment variables"). Key VALUES never go into the settings file.

Every action is one documented call of the management API (`kiko-src/docs/API-CONTRACT.md`); rex adds no new kiko
endpoint:

| Action | API call | UI behaviour |
|---|---|---|
| list | `GET /kiko/v1/models` | refresh on open, after each action, and every 30 s while visible |
| On/off (Space) | `POST /models/{name}/enabled` | enabling pings first (up to 40 s): row shows `… pinging`, a `409 ping_failed` leaves it off and shows the reason |
| Ping / Ping all | `POST /models/{name}/ping`; "all" = `GET /doctor?ping=1` | non-blocking; 4 at a time (server side); progress in the panel's info line |
| Roles... | `GET /classes`, `POST /models/{name}/roles` | a CheckBoxes list of classes + a primary RadioButtons; at least one role |
| Key... | `POST /models/{name}/key_ref` | source (default / env / keystore / dotenv) + NAME (validated as a key name, never value-shaped); "Set value..." see below |
| Export/Import | wizard 1.8 | |
| Doctor | wizard step / window 1.9 | |

**Setting a key VALUE.** The API never carries values. In embedded mode rex is the kiko process, so the "Set
value..." button opens a password InputLine (py_tvision `InputLine(password=True)`, done) and stores the value with
kikolib's own key tools: OS keystore (`kikolib.keystore`, Windows Credential Manager / macOS keychain / libsecret /
kwallet) or the kiko home `.env` (`kikolib.dotenv`) for portable installs and for FreeBSD without a desktop
keyring. The value lives in one local variable, is never logged, never shown again (only the 4-character hint the
API returns), and the field is cleared on close. In external mode the button explains that the key must be set on
the machine that runs that kiko.

|---|---|---|---|

The kiko word is always written next to the dot (`ok`, `deg`, `down`, `off`), so the state is readable in the mono
theme, on 16-colour consoles and for colour-blind users. At 80 columns the hints shrink to `F1 F2 F5 F10`, then
disappear; the indicators stay (priority order: state, ctx, kiko, model, ab, shell).

### 3.2 Threads and their rules

| Thread | Owns | May touch views? | Talks to the UI by |
|---|---|---|---|
| UI (main) | every view, the screen, the settings object, the command table | yes (only this one) | - |
| turn worker | one `Agent.stream()` call; ends with the turn | no | the coalescer + `app.post(fn)` |
| TuiAsker (runs on the turn worker) | one pending permission question | no | `app.post(open_dialog)` + a reply slot |
| kiko server threads | `kiko_runtime_lib.Server` (its own threads; `start()`, not `serve_forever`, so no signal handlers are installed) | no | nothing; rex reads it through `KikoClient` |
| HealthMonitor | `GET /health` + `/kiko/v1/status` every 3 s (1 s right after a start/stop) | no | `app.post(update_kiko_segment)` only on change |
| helper pool (max 4) | short blocking jobs (HTTP calls of 40 s pings, file export, MCP test) | no | `app.post(callback)` with the result or the error |

py_tvision already provides the pieces: one UI thread, `Program.post(fn)` (a `queue.SimpleQueue` + `terminal.wake()`,
safe from any thread), timers (`every`, `set_timer`), nested `exec_view` (a modal opened from a posted callable while
another modal runs), and a debug check of the thread id in `draw_view()` (design section 9.6). rex adds no locks to
views; every lock lives in the controllers.

The agent runs in-process (owner decision): `Agent(llm=gateway_llm(kiko_server.client().chat, model), ...)`. The
model call does not go through a socket; kiko still listens on its port so that `ai-rex` children, IDE plug-ins and
other tools use the same kiko (that is what makes the tray optional). With kiko mode `external` or `off` the agent
uses `openai_endpoint(base_url, ...)` instead.

### 3.3 How a streaming token reaches the window

1. The model adapter yields a chunk on the turn worker; the library emits `Event("token", text)`.
2. `AgentController.on_event` appends `("token", text)` to `self._pending` under a lock. If no flush is scheduled, it
   sets `self._flush_scheduled = True` and calls `app.post(self._flush)` **once**. Further tokens only append.
3. On the UI thread `_flush` swaps the list out under the lock, clears the flag, merges consecutive tokens into one
   string and calls `transcript.append_text(entry_id, merged)`. Other event kinds in the same batch are applied in
   order (tool start/end, context, notice).
4. `TranscriptView.append_text` adds to the raw markdown of the open entry and re-parses only the **open tail
   block** (the last paragraph, list or fenced code block); earlier blocks of the entry are already laid out. It
   re-wraps only those lines, updates the row count and marks itself dirty.
5. py_tvision draws once per loop turn and flushes only changed cells, at most ~60 frames per second (done). A token
   flood of thousands per second becomes one append and one frame per turn.

So the cost of a token is one list append on the worker and an amortised share of one re-wrap of the open block on
the UI thread. Long fenced code blocks are the worst case (the open block grows); the open block is re-parsed only
from its last complete line (code blocks wrap per line), so the cost stays proportional to the new text.

Tool events take the same path: `tool_start` creates a collapsed entry `▸ name summary … running`; `tool_end`
updates it (`✓`/`✗`, duration, a short result summary; the body is the result text capped at 200 lines / 64 KB with
"… N more lines" and a "View all" action; an edit result's diff is rendered with the DiffView span helpers inline).
`context` updates the status line; `notice` adds an `i`/`!` entry; `final` closes the open entry; `error` adds a red
entry with the message (one line, details in the log).

### 3.4 Permission questions

1. The engine's gate calls `asker.ask(request)` on the turn worker (`PermissionGate.set_asker`; `TuiAsker`
   implements the existing `Asker` protocol).
2. `TuiAsker` creates a reply slot (`threading.Event` + value), posts `open_permission_dialog(request, slot)` and
   waits on the slot in 100 ms steps, checking the turn's cancel flag.
3. The UI opens the dialog with `exec_view` (nested modal is fine). The button's answer is written to the slot.
4. The worker returns the answer to the gate. Stop, quit or window close while waiting writes `deny` to the slot and
   closes the dialog (`end_modal`), so the worker never hangs.

One question at a time (the loop is sequential). The tool entry shows `? asking`, then the outcome
(`allowed once`, `always`, `always for src/`, `denied`).

### 3.5 Cancellation and quit

| Trigger | What happens |
|---|---|
| Esc / Ctrl+C (no selection) / Chat > Stop / `/stop` while busy | `controller.stop()`: `agent.interrupt()` (thread-safe; the loop stops at the next chunk or step and kills a running tool's process tree, existing behaviour), a pending permission is answered `deny`, the state segment says `stopping`. The worker ends with `final`/`error`; the entry is marked `[stopped]` and the partial text stays |
| second stop within 2 s | force: close the open HTTP response of the model call (engine feature `interrupt(force=True)`, section 5); until it exists, rex shows "still waiting for the model; it will stop at the next chunk" |
| Alt-X while busy | asks "Stop the agent and quit?"; then stop, join the worker for at most 3 s, `agent.close()` (MCP servers), `kiko_server.stop(timeout=10)` (embedded only), restore the terminal (py_tvision terminal guards, done) |
| terminal closed / SIGTERM / console close | py_tvision guards restore the terminal; rex's handler calls the same quit path without asking, with shorter timeouts |
| crash in a worker | caught; becomes an `error` entry and a log record; the UI keeps running |
| crash on the UI thread | terminal restored; the traceback goes to `<install>/logs/rex.log` and one line to stderr after restore |

Threads other than the UI thread are daemon threads, so a stuck worker can never keep the process alive after quit.

### 3.6 kiko inside rex

- **Embedded (default):** `KikoHost` builds `Config(home=<install>/kiko, port=<settings port>, setup_logging=False)`
  and calls `Server(cfg).start()` on a helper thread at startup (the UI appears at once; the kiko segment shows
  `starting`). Start / Stop / Restart are menu items (a restart is a new `Server`, as the library requires). The
  management token is `srv.token` (memory only); the client uses `srv.url`.
- **Port busy:** if `GET /health` on the port already answers before start, another kiko runs (e.g. the tray's).
  rex asks once (numbered choice): 1) use that kiko (external mode, token from its `api-token` file or
  `KIKO_API_TOKEN`), 2) start rex's own kiko on the next free port. The answer is saved.
- **External:** base URL + token file path in settings; panels work as in the tray; Start/Stop are greyed (rex does
  not manage another process's service).
- **Off:** any OpenAI-compatible endpoint or LiteLLM; the kiko menu shows only "Off (Settings > Kiko)".
- **Health colours** follow the tray contract exactly: `ok`/`healthy` = green, any other answer = orange, no answer
  = red; `401` on `/kiko/v1/*` = orange with "token refused"; `404/405` = green with "management API not available".

`KikoClient` is a thin stdlib HTTP client (kikolib `http`) with one method per contract endpoint (`models()`,
`set_enabled(name, on)`, `ping(name)`, `set_roles(...)`, `set_key_ref(...)`, `export(fmt)`, `import_(fmt, body,
dry_run, retarget, prune)`, `doctor(ping)`, `keys()`, `costs(days)`, `logs(lines)`, `classes()`, `status()`). It never
logs request bodies and redacts error texts again.

### 4.2 py_tvision copied in unchanged

- Location: `vendor/py_tvision/` next to `vendor/kikolib/` (same pattern, same packaging step: copied into the
  `ai-rex` wheel / the install folder's `app/vendor/`).
- `scripts/vendor_py_tvision.py` copies `src/py_tvision` from a py-vision checkout at a **tagged commit**, writes
  `vendor/py_tvision/VENDORED.txt` (source commit, date) and `SHA256SUMS` (as kikolib has).
- `tests/test_vendor_integrity.py` fails when any vendored file differs from `SHA256SUMS`, so the copy stays
  unchanged by construction.
- Consequence: every missing toolkit piece (section 6) is built **in py-vision first** with its own step pipeline and
  tests, tagged, then re-copied. rex-specific behaviour lives in `cli/` as subclasses or compositions, never as edits
  to the copy. A rex subclass that turns out generic moves to py-vision in its next step.

- **After architecture step 14** (`lib_runtime_rex.Agent` exists): `controllers/engine.py` builds `Agent(...)` from

## 8. Test strategy

Behaviour and integration only (owner rule: no tests for getters, dataclasses, constants).

### 8.1 Headless UI tests (the bulk)

py_tvision's `HeadlessTerminal(width, height)` runs the real RexApp with scripted keys, mouse and resize
(`feed_events`, `feed_script`, `advance_auto_ticks`). Tests assert on the screen text and a compact role map (golden
snapshots in `tests/cli/snapshots/`, regenerated only with `--update-snapshots`), at 100 x 30, 80 x 25 and under the
`linux` / `cons25` profiles (16 colours, ASCII / CP437 glyphs, no mouse).

### 8.2 Fakes

- **FakeAgent / FakeLLM**: a scripted model that yields tokens at a set rate, tool calls, permission requests,
  context updates, errors and long pauses, with a deterministic clock. The real library loop runs on top of the fake
  LLM where possible (so the Asker and event path are real); pure UI tests use a FakeAgent that emits events
  directly.
- **FakeKiko**: a `kikolib.server` app on port 0 serving the contract examples (models, ping with delays, 409 on
  enable, import dry-run bodies, doctor), so panels are tested without a model or a key. Plus one integration test
  with a real `kiko_runtime_lib.Server` in a temp home (table or DB mode, no network).

### 8.3 Concurrency tests

Token flood (10 000 tokens/s for 5 s): no lost text, frame count bounded by loop turns, UI stays responsive to Esc
within 100 ms of fake time. Permission from the worker while a menu is open and while another modal runs. Stop while
asking, quit while asking, quit while a helper job (40 s ping) runs: the process ends within the documented timeouts
and no thread touches a view (py_tvision's thread-id check enabled in tests). Health monitor flapping (up / down /
up) produces only state changes, no event spam.

### 8.4 Real terminals

- POSIX `pty` smoke (test-only, as py-vision does): start `rex` with a fake model, type a prompt, answer a permission
  dialog, quit; `stty -a` equal before and after, also after a forced exception.
- Manual matrix per release (checklist, the owner or a test agent with screenshots): Windows Terminal (PowerShell
  and Git Bash), conhost, IntelliJ terminal, VS Code terminal, a Linux terminal emulator, Linux text console
  (`TERM=linux`), FreeBSD vt (`TERM=xterm`) and syscons (`TERM=cons25`) without X, macOS Terminal.app (256 colours).
  Items: frames and glyphs, colours and the kiko dot readable in mono, which F-keys and Alt keys arrive (F1, F2, F5,
  F9, F10, Alt+Enter, Ctrl+J, Ctrl+Enter), mouse click and wheel where available, paste of multi-line text,
  resize during streaming, CJK and emoji in model output, clipboard copy (OSC 52), exit restore.

### 8.5 Guards

`test_cli_layering.py` (section 4.1 rules), `test_vendor_integrity.py` (py_tvision copy unchanged),
`test_help_commands.py` (every command in the table has a help topic and a menu entry or a reason),
secret scan over snapshots, logs and `rex.toml` after the kiko tests, and a performance test: full redraw + flush of
a 200 x 60 screen with a 5 000-entry transcript under a generous bound (py-vision's own budget is 10 ms for the
toolkit part).

## 9. Risks

| Risk | Mitigation |
|---|---|
| **Scope creep** (the positioning review's main warning: "no host without a user") | strict phases; the MVP is useful alone (a better REPL with dialogs); phase 2 has a user today (the tray's job); phases 3-4 only when the owner asks |
| **py_tvision copied unchanged** makes every toolkit fix a round trip through py-vision | V1-V9 done before the MVP starts; rex subclasses for anything rex-specific; a rex-side bug found in the copy is fixed in py-vision the same day and re-vendored (the vendor script is one command) |
| **Engine not ready** (library refactor steps 6, 7, 14, 16 open) | `controllers/engine.py` adapter over today's `Session`; stderr redirected to the log while the UI runs; SIGINT not an issue in raw mode but the handler is removed by rex until step 16 |
| **Streaming cost in pure Python** (markdown re-parse, wrap) | open-block-only re-parse, per-entry wrap cache, virtualised transcript, one frame per loop turn; the token-flood test is a gate |
| **Keys swallowed** by IDE terminals, Windows Terminal (Alt+Enter), XFCE (F1, F10) | every action in a menu and most as slash commands; Ctrl+J documented for newline; key map editable; "which keys arrive" pass in the manual matrix |
| **Accidental approval** (Enter meant for the prompt hits a dialog) | no default button, 400 ms input guard, type-ahead discarded (V5); Esc = Deny |
| **Secrets in a UI** (key value entry, logs, screenshots) | values only in the embedded "Set value" dialog, password field, never stored in settings, never logged; kiko redacts and rex redacts again; tests scan snapshots and logs |
| **kiko in the same process**: a kiko bug or memory growth affects the chat | kiko runs on its own threads with `start()` (no signal handlers, `setup_logging=False`); external mode stays available; the doctor shows RSS; README records idle RAM and a soak test (lightweight-tools rule) |
| **Port conflicts** with a tray-managed kiko | port-busy rule (3.6): attach or use the next port, asked once, saved |
| **Memory growth** in long sessions | transcript bounded (old entries folded to stubs, full text stays in the session file), log view bounded, Terminal scroll-back bounded |
| **Terminal differences** (widths of emoji/CJK, 16-colour consoles, no mouse on FreeBSD syscons) | py_tvision's width rules and profiles; status words next to colours; ASCII glyph profile; the console rows of the manual matrix |
| **Debian `rex` name clash** | decided in the architecture: package `rex-tui`, command handled at packaging time; the portable folder is unaffected |
| **Inherited `AI_REX_*` variables** silently ignored could surprise a user who exported them | listed in Settings > Paths and in the doctor as warnings; documented in the help |
| **Python on FreeBSD** (needs 3.12+ from pkg; no desktop keyring) | doctor checks the version; kiko keys go to the kiko home `.env` (dotenv source) there |

## 10. Self-review (one critical pass)

- **The MVP is bigger than it looks** because it needs nine toolkit pieces first (phase 0). I kept them out of rex
  on purpose (copy unchanged, generic widgets help Layka-style apps too), but it delays the first usable rex. A
  smaller alternative: build V1 (TranscriptView) and V4/V5 (modal from thread, input guard) in py-vision, and do V3,
  V6, V7, V8 as rex-side subclasses first, upstreaming them later. That cuts phase 0 roughly in half with no loss of
  the "unchanged copy" rule. Recommended if the owner wants rex sooner.
- **In-process engine before the library is clean** is the main technical risk: stray `print` to stderr (C5) would
  scribble over the full-screen UI. The stderr redirect is a stopgap; architecture step 6 should come before phase 1
  if possible.
- **Per-hunk accept/reject was asked for** ("diffs shown in DiffView with accept/reject") but the engine cannot do it
  today. The design delivers whole-change accept/reject in the MVP and puts per-hunk in phase 4 with both
  dependencies named; it does not pretend.
- **Settings precedence** (rex ignores inherited `AI_REX_*`) is my decision; it keeps one source of truth and
  matches "rex passes its settings to ai-rex as environment". The opposite (env wins) would make the settings panel
  lie. Reversible by one flag if the owner disagrees.
- **Slash commands from `core.commands`**: the shared table does not exist yet (today's commands are registered
  inside `runtime/__main__.py`); architecture step 15 creates it. Until then rex keeps its own table with the same
  names; the help test keeps them aligned.
- **Mockups are illustrative**: column widths in a few rows were adjusted by eye; the snapshot tests will pin the
  real layout.
- **Not covered**: localisation of the UI (English first; the help system supports languages), accessibility beyond
  mono / words next to colours, and a GUI (out of scope by decision).
