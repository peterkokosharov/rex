## Архитектурата на собственика (контекст)

Библиотеката `lib_runtime_rex` е в центъра. Всичко останало е host или модул около нея.

| Част | Роля |
|---|---|
| `lib_runtime_rex` | Библиотеката в центъра на дизайна. |
| `rex/core` | Тънък headless процес. Еднократно използване: `rex -i "..." -m <model> --port 4000`. Действа и като proxy. Вграден като процес в Layka, IntelliJ и VS Code. |
| `rex/cli` | TUI на py-vision, в стила на Claude CLI и Gemini CLI. |
| `rex/ui` | GUI (Sisi). |
| `rex/web` | Уеб сървър (Lassie). |
| отделни модули | context, MCP, bridge. |

## 1. Потенциал

**Като продукт, продаван на доставчици на модели: слаб.**

- Доставчиците предлагат собствени runtime-и: Claude Agent SDK, OpenAI Agents SDK, Google ADK, NVIDIA NeMo Agent toolkit.
- Доставчиците искат lock-in. Малцина от тях биха купили библиотека на един човек.

**Като общ agent framework: претъпкан пазар.**

- Общи framework-ове: LangGraph, Pydantic AI, smolagents, LlamaIndex, CrewAI, Agno.
- Coding host-ове: aider, Goose, opencode, Codex CLI, Gemini CLI, Claude Code.

**Разликата е в комбинацията:**

| Свойство | Защо е важно |
|---|---|
| Чист stdlib, нула зависимости | Важи в Odoo virtualenv-ове, air-gapped и регулирани среди, security appliance-и, Python, вграден в C++ приложения, интерпретатори, пакетирани с IDE, и корпоративни десктопи със блокиран pip. Тази ниша никой не я държи. |
| Вграждане в процеса (in-process) | "Host-ът притежава цикъла, rex е компонент." |
| Моделът на сигурност като пълноценна функция | allow / ask / deny gate, sandbox, audit log. |
| Четим и одитируем | Под около 10 хил. реда, може да се прегледа за един ден. |

**Заключение.** Реален потенциал като "агентно ядро без зависимости и с възможност за одит, което можеш да вградиш във
всеки Python host". Никакъв потенциал като "по-добър Claude Code" или като продукт за доставчици.

## 2. Основно обещание, обхват и пропуски

**Основно обещание:**

> Агентен цикъл на Python с нула зависимости и възможност за одит, който вграждаш в собственото си приложение, като
> всяко извикване на инструмент минава през permission gate, който ти контролираш, и всяка стъпка се записва в лога.

### Какво се маха или изнася извън ядрото

- **UI-та и host-ове.** Qt UI, уеб сървър, TUI CLI и IDE plug-in-и са отделни host-ове. Правят се един по един и само
  когато някое вграждане има нужда от такъв.
- **Локален gateway.** Незадължителен. Адаптерите към доставчиците са stdlib HTTP клиенти:
  - съвместим с OpenAI, което покрива NVIDIA NIM, vLLM, Ollama и llama.cpp;
  - native Anthropic;
  - native Gemini.
- **Транспорт.** Без WebSocket в ядрото. Започва се със stdio JSON-RPC, после HTTP + SSE.
- **Sandbox.** Контейнерният sandbox е сменяем Executor. Доставя се subprocess runner с ограничена директория и
  timeout, плюс адаптер за Docker/podman.
- **Памет.** Дългосрочната памет и RAG са задача на host-а. Библиотеката предлага hook, не хранилище.

### Липсва, по приоритет

1. Структуриран trace и audit log (JSONL): извикване на модел, извикване на инструмент, решение, токени, цена.
2. Лимити за цена и бюджет на сесия: токени, пари, стъпки, реално време, с твърд стоп.
3. Възобновяеми сесии, включително асинхронно одобрение от човек часове по-късно (ключово за ERP).
4. Структуриран изход: валидиран по JSON schema, с повторен опит.
5. Evaluation harness: повторно възпроизвеждане на записани сесии срещу нов модел или prompt и проверки върху
   извикванията на инструменти.
6. Прекратяване (cancellation) и streaming като пълноценни функции.
7. Минимална поддръжка на multi-agent: "агент като инструмент".

**Правило:** loop познава само интерфейси и нищо не импортира bridge.

### Публичен API (осем обекта)

| Обект | Форма |
|---|---|
| `Agent` | `Agent(model, tools, policy, instructions, limits)`, с `.run(input) -> Result` и `.stream(input) -> events`. |
| `Model` | Protocol `complete(messages, tools)`, плюс `connect("nemotron-ultra")`. |
| `Tool` | `Tool` и декоратор `@tool`. |
| `Policy` | Правила плюс ask callback, който може да върне "pending". |
| `Session` | save/load през протокол `Store`. |
| `Limits` | Бюджети на сесия. |
| `Event` | Едно семейство dataclass-ове. |
| `MCPServer` | |

Водещо правило: ако нов обект не може да се обясни с един ред, той не влиза.

## 4. Рискове

| Риск | Смекчаване |
|---|---|
| **Дрейф на доставчиците.** | Поддържат се само съвместими с OpenAI, Anthropic и Gemini. Contract тестове със записани fixture-и. Останалите доставчици стават адаптери на общността. |
| **Болката на stdlib.** Синхронен код и нишки; без точно броене на токени. | Токените се оценяват и се коригират по данните за употреба от доставчика. Никога не се обещава точно броене. |
| **Разрастване на обхвата** върху 4 host-а и 5 приложения. Най-вероятната причина за смърт на проекта. | Библиотека плюс точно едно реално вграждане до v1. Никакъв host без потребител. |
| **Приемане:** "защо не Pydantic AI или LangGraph?" | Пазарна позиция в нишата: 0 зависимости, работи вътре в Odoo, ядро от X реда, всяко действие е одитирано. Една впечатляваща демонстрация. |
| **Неверни твърдения за сигурност.** | Deny по подразбиране. Изходът на инструментите се третира като недоверен. Gate-ът стои извън обсега на модела. Рано се пише документ с threat model. Външно ревю, преди да се употреби думата "secure". |

## 5. Етапи

**M1 - Odoo copilot, само за четене.**

- Addon-ът импортира библиотеката in-process; без pip в средата на Odoo.
- Инструменти за ORM търсене и четене. Всеки запис е отказан.
- Реални въпроси, например "неплатени фактури над 30 дни за клиент X".
- Trace лог и лимити за цена.
- Работи с един облачен и един локален доставчик.

**M2 - записи през gate и възобновяемо одобрение.**

- Агентът предлага чернова на фактура или промяна на наличност.
- Policy е "ask"; сесията се запазва.
- Потребителят одобрява по-късно в интерфейса на Odoo; сесията се възобновява.
- Изглед на audit log; структурирани предложения.

**M3 - втори, много различен host през bridge.**

- Headless stdio JSON-RPC от редактор или от C++ TUI при същия Policy, или host за наблюдение/чатбот.
- Replay evaluation harness, изграден от сесиите на M1-M2 и пускан върху различни модели.
- После v1. Едва след това се обмислят CLI, Qt и уеб host-ове.

## Заключение

ако първо бъде доказан в Odoo.
